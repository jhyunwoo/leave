# 외부 캘린더 — 리브 일정을 아이폰·구글·갤럭시 캘린더에서 본다

## 문제

리브에 적은 일정은 리브 안에서만 보인다. 사용자는 하루를 아이폰 기본 캘린더, 구글
캘린더, 삼성 캘린더에서 시작하는데, 거기에는 다음 주 외박도, 부대 행사도 없다. 그래서
약속을 잡을 때마다 리브를 따로 열어 보거나, 같은 일정을 손으로 한 번 더 적는다.
손으로 옮긴 일정은 리브에서 날짜를 바꾸는 순간 틀린 정보가 된다.

이 기능은 반대 방향이다. `2026-09-20-device-calendar-overlay-design.md`가 기기 캘린더를
리브로 **읽어 들이는** 설계라면, 이것은 리브 일정을 바깥 캘린더로 **내보낸다.**

## 결정된 요구사항

브레인스토밍에서 확정한 것:

- **대상은 다섯 가지 전부다.** 외출, 외박, 휴가(= 휴가 한 건과 그 구간들), 개인 일정,
  부대 일정.
- **두 갈래로 내보낸다.**
  1. **구독 URL(.ics)** — 모든 기기. 아이폰 캘린더와 구글 캘린더가 주기적으로 받아 간다.
  2. **기기 캘린더 직접 쓰기** — **모든 안드로이드**(갤럭시 포함). 삼성 캘린더는 URL
     구독을 지원하지 않아서, 구독 URL만으로는 구글 계정을 거쳐야 한다.
- **초안도 내보낸다.** 제목 앞에 `(초안)`을 붙여 구분한다. 반려·취소는 내보내지 않는다.
- **세부 내용까지 다 담는다.** 제목·사유·메모·시간·부대 일정 세부까지. 대신 기능은 기본
  꺼짐이고, 링크 재발급 한 번으로 예전 URL을 즉시 죽일 수 있다.
- iOS 기기 캘린더 직접 쓰기는 하지 않는다. 아이폰은 구독 URL이 기본 캘린더에 그대로
  붙는다.

## 배포 — 두 번에 나눈다

| 릴리스 | 내용 | 경로 |
|---|---|---|
| 1 | 구독 URL, API, 웹, 앱 설정 화면 | 서버 배포 + 웹 배포 + **OTA** |
| 2 | 안드로이드 기기 캘린더 쓰기 | **새 EAS 빌드 + 스토어 심사** |

릴리스 1은 새 네이티브 모듈이 없다. `expo-clipboard`와 `expo-linking`은 이미 들어 있다.

릴리스 2는 `expo-calendar`를 새로 넣는다. `app.json`의 `runtimeVersion.policy`가
`"fingerprint"`이므로 **OTA로는 절대 닿지 않는다.** 네이티브 모듈은 두 플랫폼 지문을 모두
바꾸므로 iOS에서는 쓰지 않더라도 **iOS도 새 빌드가 필요하다.** 심사 대기가 릴리스 1을
붙잡지 않도록, 릴리스 2는 다음 스토어 빌드에 태운다. 절차는 `deploy-app` skill을 따른다.

## 설계

### 1. 피드 항목 — 한 곳에서 만들고 두 형식으로 내보낸다

서버에 순수 함수 `buildFeedItems`를 둔다. 구독 URL(.ics)과 안드로이드 동기화(JSON)가
**같은 항목 목록**을 받는다. 규칙(초안 표시, 취소 제외, 조회 범위)이 두 벌이 되면
아이폰과 갤럭시가 같은 계정에서 다른 일정을 보여 준다.

```ts
type FeedItem = {
  /** 안정 식별자. 외부 캘린더가 이 값으로 "같은 일정"을 알아본다. */
  uid: string; // "leave-<id>" | "personal-<id>" | "unit-event-<id>"
  title: string;
  description: string | null;
  startDate: ISODate; // 포함 시작
  endDate: ISODate; // 포함 끝
  startTime: LocalTime | null; // null이면 종일
  endTime: LocalTime | null;
};
```

`updatedAt`은 두지 않는다. `leaves`에는 수정 시각 컬럼이 없고, 구독 캘린더는 매번 피드
전체를 받아 바꿔 끼우므로 `LAST-MODIFIED`가 없어도 갱신된다.

자리: 순수 조립은 `packages/shared/src/calendar-feed.ts`, 렌더러는 `packages/shared/src/ics.ts`, 조회는 `apps/api/src/lib/calendar-feed.ts`. 응답이 "누가 보느냐"에 따라
달라지는 점은 `lib/calendar.ts`와 같다 — 이 응답을 캐싱하려면 키에 사용자 id가 반드시
들어가야 한다.

**조회 범위:** 오늘(서울) 기준 6개월 전부터 앞으로 전부. 종료일이 범위 시작 이후인 것만
가져온다. 지난 일정을 끝없이 실으면 피드가 커지고 구글이 큰 피드를 늦게 받는다.

**휴가 (외출·외박·휴가)** — 휴가 한 건 = 일정 하나.

- 구간마다 쪼개지 않는다. "연가 4일 + 정기외박 4일"은 한 번의 출타이고, 바깥 캘린더에서
  두 칸이 맞붙어 보이면 두 번 나가는 것처럼 읽힌다.
- 제목 머리: 구간이 전부 외출이면 `[외출]`(`isOutingSegments`), 전부 외박이면 `[외박]`,
  그 밖에는 `[휴가]`. 그 뒤에 휴가 제목. 초안이면 맨 앞에 `(초안)`.
  예: `(초안) [휴가] 여름 휴가`.
- 종일 일정으로 `startDate`~`endDate`.
- 설명: 구간 목록(`8/2~8/5 연가 · 8/6~8/9 정기외박`, 이름은 `balanceLabel`), 진행 상태
  (`LEAVE_STATUS_LABELS`), `복귀 21:00`, 사유.
- 상태: `rejected`·`cancelled`를 뺀 전부.

**개인 일정** — 제목·메모 그대로.

**부대 일정** — 지금 소속 그룹의 것만. 제목 앞에 `[그룹 이름]`, 설명은 세부 내용.
그룹을 나가면 다음 갱신 때 사라진다.

**시간 규칙** (개인·부대 일정. 스키마상 시작·끝 시간이 각각 비어 있을 수 있다):

- 시작 시간이 있고 (끝 시간이 있거나 하루짜리)일 때만 시각 일정이다. 시작 시간만 있는
  하루짜리는 끝을 두지 않는다(RFC 5545: DTEND가 없으면 시작 시각에 끝난다).
- 나머지(시작 시간이 없거나, 여러 날짜에 시작 시간만 있는 경우)는 종일 일정이고, 시간이
  있으면 설명 첫 줄에 `HH:mm~HH:mm`으로 적는다.

### 2. 구독 URL

**저장** — 마이그레이션 `0039_calendar_feeds.sql`:

```ts
export const calendarFeeds = sqliteTable("calendar_feeds", {
  userId: text("user_id")
    .primaryKey()
    .references(() => users.id, { onDelete: "cascade" }),
  token: text("token").notNull().unique(),
  createdAt: text("created_at").notNull(),
});
```

- 토큰은 `generateSessionToken()`과 같은 강도의 무작위 문자열이다.
- **토큰은 해시하지 않고 원문으로 저장한다.** 세션 토큰은 해시하지만 이유가 다르다.
  세션 토큰은 쓰기 권한까지 주지만 이 토큰은 DB에 이미 있는 일정을 읽게만 한다. DB를
  읽을 수 있는 사람은 토큰 없이도 일정을 본다. 반대로 원문이 있어야 사용자가 나중에
  링크를 다시 복사할 수 있다(아이폰에 붙인 다음 날 구글에 붙이기).
- `delete-account.ts`의 삭제 목록에 적는다. 외래키 cascade로도 지워지지만, 그 파일은
  "무엇이 지워지는가"를 한 곳에서 읽게 하려고 외래키가 있는 표도 적어 둔다.

**API** (인증 필요, `routes/calendar-feed.ts`를 `/calendar-feed`에 붙인다):

| 경로 | 동작 |
|---|---|
| `GET /calendar-feed` | `{ url: string \| null }` |
| `POST /calendar-feed` | 만들거나 **재발급**. 새 토큰으로 덮어써 예전 URL은 즉시 404 |
| `DELETE /calendar-feed` | 끄기. 행을 지운다 |

**피드** (인증 없음): `GET /calendar/:token.ics`

- `index.ts`에 `/calendar` 라우트로 붙인다. 최소 버전 미들웨어는 `X-Client-Version`이
  없으면 통과시키므로 캘린더 앱의 요청이 막히지 않는다.
- 모르는 토큰은 404. 존재 여부 말고는 아무것도 알려 주지 않는다.
- rate limit은 **피드 주인 단위**다. 토큰으로 주인을 찾아 `c.set("user", …)`한 뒤
  `rateLimit({ name: "calendar-feed", limit: 60, windowSeconds: 600 })`를 건다. 기본
  키인 IP를 쓰면 안 된다 — 구글은 모든 사용자의 피드를 같은 IP 대역에서 받아 가서,
  한 사람의 피드가 모두의 갱신을 막는다. 토큰 대입은 256비트 무작위라 막을 필요가 없다.
- 접속 기록(`access_logs.path`)에는 `/calendar/:token`으로 가려 저장한다. 관리 화면이
  그 표를 읽는다.
- 헤더: `Content-Type: text/calendar; charset=utf-8`, `Cache-Control: private, max-age=300`.
- 응답 URL은 `API_ORIGIN` 환경변수로 만든다(인증 메일 링크와 같은 이유 — wrangler dev가
  요청 주소를 바꿔 보낸다).

### 3. ICS 생성 — 조용히 깨지는 곳

순수 함수 `apps/api/src/lib/ics.ts`의 `renderIcs(items, { calendarName })`. 틀려도 오류가
나지 않고 **캘린더 앱이 일정을 말없이 버리거나 하루 밀어 그린다.** 그래서 규칙을 전부
테스트로 박는다.

- 줄 끝은 `CRLF`.
- **줄 접기는 75 *바이트* 기준이다.** 한글은 UTF-8로 3바이트라 글자 수로 자르면 줄이
  넘치고, 바이트로 자르되 **글자 중간에서 자르면 안 된다.** 이어지는 줄은 공백 하나로 시작.
- TEXT 이스케이프: `\` → `\\`, `;` → `\;`, `,` → `\,`, 줄바꿈 → `\n`.
- **종일 일정의 `DTEND`는 배타적이다.** `endDate + 1일`을 `VALUE=DATE`로 적는다. 그대로
  적으면 모든 휴가가 하루 짧게 보인다.
- 시각 일정은 `TZID=Asia/Seoul`과 `VTIMEZONE` 블록(UTC+9, 서머타임 없음)을 함께 싣는다.
- `UID`는 `<item.uid>@leave.moveto.kr`. 매번 같은 값이어야 캘린더가 일정을 갱신하고,
  달라지면 중복으로 쌓는다.
- `DTSTAMP`는 응답 시각(UTC).
- 캘린더 머리: `X-WR-CALNAME:리브`, `X-WR-TIMEZONE:Asia/Seoul`,
  `REFRESH-INTERVAL;VALUE=DURATION:PT1H`, `X-PUBLISHED-TTL:PT1H`. 갱신 주기는 결국 각 앱이
  정하지만, 아이폰은 이 값을 참고한다.

### 4. 안드로이드 기기 캘린더 쓰기 (릴리스 2)

**데이터** — 인증 엔드포인트 `GET /calendar-feed/items`가 `buildFeedItems`의 결과를
JSON으로 준다. 구독 URL을 켜지 않아도 쓸 수 있다(토큰과 무관).

**자리** — `apps/native/src/device-calendar-export/`. 모양은 `widgets/`를 따른다.

```
preferences.ts                 켜짐 여부 + 만든 캘린더 ID + 마지막 동기화 해시 (기기 로컬)
bridge.ts / bridge.native.ts   expo-calendar 얇은 감싸개 (웹·iOS는 no-op)
calendar-export-sync.native.tsx  화면 없는 동기화 컴포넌트
```

`packages/client`가 아니라 `apps/native`다. client는 웹과 공유하므로 `expo-calendar`를
import할 수 없다.

**리브 전용 캘린더** — 처음 켤 때 `리브`라는 로컬 캘린더를 하나 만들고
(`ACCOUNT_TYPE_LOCAL`), **그 안에만 쓴다.** 사용자의 다른 캘린더는 읽지도 고치지도 않는다.
끌 때는 그 캘린더를 통째로 지운다.

**동기화 = 바뀌었으면 다시 쓴다**

1. 항목을 받아 내용 해시를 만든다.
2. 마지막 동기화 해시와 같으면 끝.
3. 다르면 `리브` 캘린더의 일정을 모두 지우고 다시 쓴다. 해시를 저장한다.

일정별로 차이를 맞추는 방법보다 느리지만, 한 사용자의 일정은 많아야 수백 건이고 **어긋날
수가 없다.** 어긋난 동기화가 남기는 유령 일정은 틀린 날짜를 믿게 만든다.
`리브` 캘린더가 기기에서 사라졌으면(사용자가 지움) 해시를 버리고 새로 만든다.

**종일 일정은 UTC 자정으로 쓴다.** 안드로이드 캘린더 제공자는 종일 일정을 UTC로
저장하도록 요구한다. 서울 자정(= 전날 15:00 UTC)으로 쓰면 삼성 캘린더에서 하루 앞당겨
보인다. 이 변환은 `bridge.native.ts` 한 곳에서 하고 단위 테스트로 박는다.

**언제** — `widget-sync.native.tsx`와 같은 방식이다. 인증 상태에 따라 컴포넌트를 갈아
끼우고, `RootNavigator`에 둔다.

- 앱을 열 때, 포그라운드로 돌아올 때.
- 휴가·개인 일정을 저장·삭제한 뒤. 그 mutation들이 이미 무효화하는 쿼리 키 옆에
  `calendar-items` 키를 함께 무효화하고, 동기화 컴포넌트는 그 쿼리 결과가 바뀌는 것을 본다.
- 설정에서 켤 때.

**한계 — 앱이 실행될 때만 맞춘다.** 관리자가 부대 일정을 바꾸면 사용자가 리브를 다음에 열
때 반영된다. 백그라운드 작업은 이번 범위에서 뺀다. 설정 화면에 한 줄로 적는다.

**로그아웃·탈퇴·401** — `리브` 캘린더를 지운다. `clearPersistedQueryCache()`를 부르는
자리와 같은 곳이다. 같은 휴대폰을 다른 사람이 쓰면 남의 일정이 남는다.

**권한과 설정** (`app.json`):

- `plugins`에 `expo-calendar`.
- `android.permissions`에 `READ_CALENDAR`, `WRITE_CALENDAR`. 우리 캘린더를 찾고 지우려면
  읽기도 필요하다.
- iOS 사용 문구는 플러그인이 넣는 기본값을 쓰지 않고 한국어로 적는다. iOS에서 권한을
  요청하는 코드는 없다.
- Play Console 데이터 보안 양식: "캘린더 — 기기에서만 쓰고 수집·전송하지 않음".

**기기 캘린더 겹쳐보기와의 관계** — `2026-09-20-device-calendar-overlay-design.md`가
구현되면 이 `리브` 캘린더와 구독 캘린더가 리브 달력에 **다시 그려져 중복된다.** 그 설계는
쓰기 가능한 캘린더만 기본으로 켠다. 구독 캘린더는 읽기 전용이라 빠지지만 `리브` 로컬
캘린더는 쓰기 가능이다. 겹쳐보기를 구현할 때 **우리가 만든 캘린더 ID는 목록에서 뺀다.**

### 5. 화면

**앱** — 프로필 탭 위젯 카드 아래에 `외부 캘린더` 카드. 새 화면 `calendar-export`
(라우트 등록은 `widget-settings`와 같은 자리).

- 안드로이드: 맨 위에 **`휴대폰 캘린더에 바로 추가`** 토글(릴리스 2). "앱을 열 때마다
  맞춰요" 안내 한 줄.
- 구독 URL 영역(공통):
  - 꺼짐: `구독 링크 만들기` 버튼 하나.
  - 켜짐: `iPhone 캘린더에 추가`(`webcal://` 링크, iOS만), `Google 캘린더에 추가`
    (`https://calendar.google.com/calendar/r?cid=<webcal URL 인코딩>`), `링크 복사`,
    `링크 재발급`, `끄기`.
  - 안내: 구글 캘린더는 반영까지 최대 하루 걸릴 수 있음, 링크를 가진 사람은 일정을 볼 수
    있으니 공유하지 말 것.
- `링크 재발급`과 `끄기`는 확인을 한 번 받는다. 이미 붙여 둔 캘린더가 끊긴다.

**웹** — 프로필 페이지에 같은 구독 URL 영역. 안드로이드 토글은 없다.

훅(`useCalendarFeed`, 만들기·재발급·끄기 mutation)은 `packages/client`에 둔다.

## 오류 처리

- 피드 조립이 실패하면 500. 캘린더 앱은 이전에 받은 일정을 그대로 두므로 빈 피드를
  돌려주는 것보다 안전하다. **빈 200은 모든 일정을 지우라는 뜻이다.**
- 안드로이드 동기화 실패(권한 회수, 캘린더 제공자 오류)는 `captureHandledError`로 남기고
  앱은 계속 쓴다. 권한이 회수됐으면 설정 화면 토글을 꺼짐으로 보여 준다.

## 테스트

- **안드로이드 날짜 변환 단위 테스트:** 종일 일정의 UTC 자정 변환, 시각 일정의 서울 시각.
- **ICS 단위 테스트:** 한글 긴 제목의 바이트 접기(75바이트 이하, 글자 안 깨짐),
  이스케이프, 종일 `DTEND` +1일, 시작 시간만 있는 일정, `VTIMEZONE` 포함.
- **피드 항목 단위 테스트:** 외출·외박·혼합 휴가의 제목 머리, `(초안)`, 반려·취소 제외,
  6개월 범위, 부대 일정의 그룹 이름.
- **API 통합 테스트** (`apps/api/test/calendar-feed.test.mjs`): 만들기 → 피드 200,
  재발급 → 예전 토큰 404, 끄기 → 404, 모르는 토큰 404, **다른 사용자의 휴가·개인 일정이
  섞이지 않음**, 그룹을 나가면 부대 일정이 빠짐, rate limit.
- **실제 파서 검증:** 테스트 데이터로 만든 피드를 표준 iCalendar 파서(Python `icalendar`)로
  읽어 일정 수와 날짜가 맞는지 확인.
- **실기 확인:** 릴리스 1은 아이폰 구독과 구글 캘린더 추가를 손으로 확인. 릴리스 2는
  갤럭시에서 켜기 → 삼성 캘린더에 `리브` 캘린더 표시 → 휴가 수정 → 반영 → 로그아웃 →
  캘린더 사라짐.
