# 코드 스타일

서식은 다루지 않는다 — Prettier가 전담하고 `pnpm format`이 고친다.
여기 있는 것은 "고치기 안전한 코드"를 위한 규칙이다.

## 도구가 지키는 것

| 규칙                                      | 도구                                      |
| ----------------------------------------- | ----------------------------------------- |
| 서식                                      | Prettier (`pnpm format:check`)            |
| 안 기다린 Promise, 죽은 코드, switch 누락 | ESLint 타입 인식 규칙 (`pnpm lint`)       |
| 의존 방향                                 | ESLint `no-restricted-imports`            |
| 타입 엄격성                               | `tsconfig.base.json` (`pnpm check-types`) |
| 설정↔코드 바인딩 어긋남                   | `bindings-drift.ts`, `pnpm types:check`   |

규칙을 끄는 것은 괜찮다. **이유 없이** 끄는 것이 아니다.
`eslint-disable`에는 왜 그 자리에서만 예외인지 한 줄로 적는다.

## 주석

```
코드는 무엇을 하는지 말한다.
주석은 왜 그런지, 무엇이 제약인지, 무엇이 정책인지 말한다.
```

남길 가치가 있는 것: 군 휴가 규정, 운영·개인정보 정책, 보안 판단, 캐시 무효화 근거,
D1/R2/Workers의 특이한 제약, 플랫폼 우회, 과거에 실제로 났던 사고.
지울 것: 코드를 그대로 옮겨 적은 문장.

이름으로 해결되는 것은 이름으로 해결한다. 주석으로 이름을 변호하지 않는다.

## 이름

의도를 드러내는 이름을 쓴다. `data`, `item`, `handle`, `process`, `util`, `manager`, `helper`처럼
아무 데나 붙는 이름 대신 도메인 낱말을 쓴다 — `deleteAccount`, `joinUnitByInviteCode`,
`ensureDefaultAnnualGrant`, `LEAVE_MUTATION_KEYS`.

바깥으로 나간 이름(API 필드, 쿼리 키, 저장소 키)은 취향으로 바꾸지 않는다.

## 파일 크기와 복잡도

줄 수 상한을 두지 않는다. 응집된 500줄 파일이 뜻 없는 50줄 열 개보다 낫다.
크기는 "한 번 들여다볼 이유"이지 그 자체로 문제가 아니다.

쪼갤 이유가 되는 것은 다음이다.

- 바뀌는 이유가 둘 이상이다 (관리자 워커의 `leaves-content.ts`가 휴가·초대코드·신고·알림을 함께 들고 있었다)
- 읽으려면 서로 무관한 지식이 필요하다
- 추상화 수준이 섞여 있다 (HTTP 상태 코드 고르기와 SQL 실행 순서가 한 함수에)
- 테스트하기 어렵다
- 같은 도메인 규칙이 다른 곳에도 적혀 있다

쪼개기 전에 묻는다: **떼어낸 부분에 정확한 책임 한 줄을 붙일 수 있는가?**
붙일 수 없으면 아직 쪼갤 때가 아니다.

## 중복

지식 중복과 우연히 닮은 코드를 구분한다.

서버·웹·앱이 같은 답을 내야 하는 규칙이 여러 곳에 적혀 있으면 `packages/shared`로 내린다.
반대로, 웹의 `<div>`와 네이티브의 `<View>`가 비슷해 보인다고 공용 컴포넌트를 만들지 않는다.
나쁜 추상화보다 약간의 중복이 낫다.

## 계층 만들기

계층을 하나 더 두기 전에 묻는다: **이 계층이 격리하는 구체적인 책임이 무엇인가?**

모든 CRUD에 Controller → Service → Repository를 깔지 않는다.
Drizzle 한 줄 조회에 Repository·DAO·Mapper를 씌우지 않는다.
저장 헬퍼를 만드는 것은 같은 쿼리를 재사용하거나, 쿼리 자체가 복잡하거나,
한 작업이 여러 저장 연산을 순서대로 엮을 때다.

상태를 들지 않는다면 클래스보다 함수와 모듈을 쓴다.

## 타입

- `any`를 쓰지 않는다. 경계에서는 `unknown`으로 받고 좁힌다.
- 어쩔 수 없는 캐스팅은 좁은 경계 한 곳에 모으고 이유를 적는다
  (관리자 화면의 `format.ts`가 그런 자리다).
- 신뢰할 수 없는 런타임 경계(요청 본문, 저장된 JSON)에서만 zod로 검증한다.
  컴파일 타임에 이미 보장되는 곳에 런타임 검증을 덧대지 않는다.
- 프레임워크 타이핑 한계로 규칙이 걸리면, 끄기 전에 그것이 정말 한계인지 먼저 확인한다.

## React

effect를 쓰기 전에 묻는다: **React를 외부 시스템과 맞추고 있는가?**

그렇다면 쓴다(구독, 저장소, 타이머, 포커스, 플랫폼 API, 네트워크 수명주기).
아니라면 대개 렌더 중 계산·이벤트 처리·구조로 풀 수 있다.

- 렌더 중에 구할 수 있는 값을 state로 복사하지 않는다.
- 조건이 바뀌었을 때 state를 되돌려야 한다면, effect보다 렌더 중 조정이나 다시 마운트가 낫다.
  (`EntityPage`의 페이지 번호 초기화, `ConfirmDialog`의 입력 초기화가 그 예다.)
- 서버 상태는 TanStack Query에 둔다. Jotai/`useState`는 화면 상태만 갖는다.

## 변경 단위

한 커밋에 서식·이름 바꾸기·구조 변경·동작 변경을 섞지 않는다.
코드를 옮길 때는 ① 먼저 그대로 옮기고 ② 동작을 확인하고 ③ 그 다음에 다듬는다.
