# 아키텍처

이 문서는 "무엇이 어디에 사는가"와 "왜 그 자리인가"를 다룬다.
명령어와 실행 방법은 [README.md](../README.md), 에이전트용 작업 규칙은 [AGENTS.md](../AGENTS.md)에 있다.

## 패키지와 책임

| 경로              | 한 줄 책임                                     | 담지 않는 것                                |
| ----------------- | ---------------------------------------------- | ------------------------------------------- |
| `packages/shared` | 플랫폼과 무관한 도메인 규칙(순수 함수·zod)     | React, 네트워크, DB, 런타임 전역            |
| `packages/client` | 웹·앱이 함께 쓰는 데이터 계층(쿼리 훅·폼 상태) | 화면(JSX), 스타일, localStorage/SecureStore |
| `apps/api`        | 공개 API 워커 (Hono + D1 + KV)                 | 화면, 클라이언트 캐시 정책                  |
| `apps/web`        | 웹 화면 (Vite + React)                         | 도메인 규칙, 서버 상태 사본                 |
| `apps/native`     | iOS/Android 화면 (Expo)                        | 도메인 규칙, 서버 상태 사본                 |
| `apps/admin`      | 운영자 콘솔 (SPA + 전용 워커)                  | 사용자 앱과 공유하는 화면                   |

## 의존 방향

```
        packages/shared          ← 아무것도 위로 의존하지 않는다
         ↑     ↑      ↑
         │     │      └──────── apps/admin
         │     └───────────── apps/api
   packages/client
         ↑        ↑
   apps/web   apps/native
```

- `apps/admin`은 서버 전용 경계 `@leave/api/server`(apps/api/src/admin-shared.ts)로 스키마와 암호·푸시 헬퍼를 가져온다.
  브라우저 번들에서는 import하지 않는다.
- `packages/client`는 `@leave/api`에서 **타입만** 가져온다(`AppType`). Hono RPC가 성립하는 지점이며,
  값 import는 서버 코드를 클라이언트 번들로 끌어온다.
- 웹과 네이티브는 서로의 구현을 모른다. 공유할 것이 생기면 아래로 내린다.

이 규칙은 문서가 아니라 도구가 지킨다 — `eslint.config.mjs`의 `no-restricted-imports`가 어긋난 import를
오류로 만든다. 예외를 두려면 그 파일에 이유와 함께 적는다.

## 어디에 두는가

**순수한 휴가·달력 규칙** → `packages/shared`.
서버와 두 앱이 같은 답을 내야 하는 것은 전부 여기다(잔여 계산, 정기외박 주기, 계급 진급, 날짜 표기).
Date 객체를 밖으로 내보내지 않는 것이 이 패키지의 규칙이다 — 타임존 때문에 하루가 밀리는 사고를 막는다.

**휴가 상태를 세는 목록이 둘인 것은 의도다**(`shared/leave.ts`). `COUNTED_LEAVE_STATUSES`는
"그날 그룹에서 몇 명이 나가는가"에 답하고 초안을 뺀다 — 나만 보는 계획이 남의 출타율에
들어가면 안 된다. `BALANCE_LEAVE_STATUSES`는 "내 통장에서 며칠이 빠지는가"에 답하고
초안을 넣는다(계획도 잡아 둔 몫이다). 대신 `rejected`·`cancelled`는 둘 다에서 빠진다.
헷갈려서 아무 조건도 걸지 않으면 취소한 휴가가 잔여를 계속 깎고, 한쪽을 다른 쪽에 쓰면
"칩은 여유가 있는데 저장하면 400"이 난다 — 둘 다 실제로 났던 일이다. 클라이언트에서
구간을 모을 때는 `@leave/client`의 `balanceCountedSegments` 하나만 쓴다.

**주기 재원은 둘이고 산술은 하나다.** 정기외박과 외출이 같은 모양의 설정
(언제부터·얼마마다·회당 몇)에서 주기를 파생하므로, 주기 산술은 `shared/leave-cycle.ts`에
한 벌만 둔다. 그 위에 재원별 판정이 얹힌다 — `regular-overnight.ts`, `outing.ts`.
둘을 따로 구현하면 달 단위 말일 처리 같은 것이 한쪽에서만 고쳐진다.

**외출은 일이 아니라 횟수다.** 부대관리훈령의 외출은 당일 복귀이므로(밤을 넘기면 외박이다)
세 가지가 함께 따라온다.

- 구간은 하루다(`leaveCreateSchema`). 그래서 주기를 걸칠 수 없고, 정기외박이 필요로 하는
  차감 주기 선택(`regularOvernightCycleStart`)이 외출에는 없다.
- 외출은 다른 재원과 한 휴가로 묶이지 않고 이웃과 병합되지도 않는다(`leave-merge.ts`의
  `hasOuting`). 묶이면 붙어 있는 외출 둘이 이틀짜리 구간으로 접혀 횟수가 사라지고,
  합쳐진 휴가의 마지막 날이 외출이면 출타 집계가 그 날을 복귀일로 보고 빼 버린다.
- "남은 휴가 N일" 합계에 더하지 않는다(서버 `leave-grants.ts`의 `cycleSum`, 클라이언트
  `summarizeHoldings`). 두 자리가 갈리면 보유 휴가 화면과 내 휴가 카드가 다른 수를 말한다.
- **부대 출타 집계에 넣을지는 부대가 고른다**(`units.outingCounts`, 기본은 셈). 일과 후
  외출을 하루 최대 출타 인원 한도에 넣는 부대와 넣지 않는 부대가 갈려 하드코딩할 수 없다
  — `units.returnDayCounts`와 같은 이유다. 남은 일과일은 이 설정과 무관하게 언제나 외출을
  뺀다(`lib/duty-days.ts`): 저기는 "그날 일과가 사라지는가"를 묻고 부대가 고를 여지가 없다.
- 단위 표기는 `balanceUnitLabel` 하나를 쓴다(외출만 "회").

**갈래를 나누는 것은 규정이 아니라 운용이다.** 평일 외출과 주말 외출은 횟수가 따로
관리돼(육군 기준 월 2회 · 월 1회) 설정도 주머니도 갈래마다 한 벌씩이다. 군별 기본값과
그 근거는 `shared/outing-guidance.ts`에 있고, 근거가 약한 값은 켜지 않는다 — 해·공군의
주말 외출 주기는 공개 규정에 없어 기본이 꺼짐이다. 여기서도 **군종은 제안값만 주고
상한은 주지 않는다.**

**같은 날짜를 두 번 세지 않는다.** 상태가 다른 두 휴가는 겹칠 수 있다(초안으로
시뮬레이션한 뒤 실제 휴가를 만드는 흐름 — `leave-merge`의 겹침 검사는 같은 상태끼리만
본다). 그래서 `usageDates`와 `cycleUsedDays`는 합계가 아니라 **날짜 집합의 크기**를 센다.
하루에 두 번 나갈 수는 없다.

**웹/앱의 서버 데이터 접근** → `packages/client/src/hooks`.
화면에서 `useQuery`를 직접 부르지 않는다. 캐시 키는 `query-keys.ts` 한 곳에서만 만들고,
"이 뮤테이션 뒤에 무엇이 낡는가"는 `hooks/invalidate.ts`의 묶음으로 이름 붙여 둔다.

**플랫폼 차이**(토큰 저장소, 인증 실패 시 정리) → `LeaveApiAdapter`. 앱 루트에서 한 번 주입한다.

**홈 화면 위젯** → `apps/native/src/widgets`. 위젯은 새로고침할 때 JS를 돌릴 수 없어
앱이 앞으로 14일치 값을 미리 밀어 넣는다. 그 구조와 플랫폼별 제약은 [widgets.md](widgets.md)에 있다.

**서버 상태 vs 화면 상태** → TanStack Query가 서버 상태를, Jotai/`useState`가 화면 상태를 가진다.
지금 Jotai가 들고 있는 것은 세션 토큰 하나뿐이다.

**친구와 개인 일정** → 친구 관계는 사용자 쌍을 정렬한 `friendships` 한 행으로 표현하고
`pending`/`accepted` 상태와 요청자를 따로 기록한다. 친구 달력은 매 요청마다 수락 상태와 양방향 차단을
다시 확인하고, 집계 대상 휴가의 날짜·상태만 반환한다. `personal_events`는 휴가와 별도인 소유자 전용
엔티티다. 따라서 개인 일정은 부대 달력 통계·휴가 잔여·알림 쿼리에 들어갈 수 없다.

친구 관계에서 생기는 알림(요청 도착, 친구의 새 휴가)은 `lib/social-notify.ts`가 만든다.
받는 사람을 고르는 규칙이 친구 달력과 같다 — **수락된** 관계만, 어느 방향으로든 차단이
있으면 제외, 종류별 수신 설정을 끈 사람 제외. 초안 휴가는 알리지 않는다(나만 보는
계획의 존재 자체가 새면 안 된다). 친구 수만큼 행이 늘어나므로 `insertStatements`로
나눠 담는다.

`pending`이 `accepted`로 가는 길은 **받는 사람의 명시적 수락 하나뿐**이다(`lib/social.ts`).
예전에는 반대 방향 요청이 자동으로 수락으로 수렴했는데, 그러면 받는 사람이 수락을 누른 적 없이
자기 일정이 공개된다. 지금은 409(`incoming_request_exists`)로 돌려보내고 화면이 수락/거절을 묻는다.

**공개 사용자 이름(@아이디)** → 친구 찾기의 유일한 공개 식별자다. 규칙과 정규형은
`packages/shared/src/username.ts` 한 곳에만 있고, 유일성은 앱이 아니라 `users_username_idx`
유니크 인덱스가 지킨다 — "조회하고 없으면 넣는다"는 동시 요청 두 건 사이에서 반드시 깨진다.
이메일로 친구를 찾을 수 있으면 요청 결과가 곧 "이 주소로 가입했는가"에 대한 답이 되어
친구 기능이 이메일 열거 수단이 되므로, 이메일 기반 친구 추가는 0023에서 걷어냈다.
프로필 링크와 딥링크의 전체 그림은 [deep-links.md](deep-links.md)에 있다.

## API 워커 구조

```
routes/<기능>.contract.ts   이 API가 약속하는 것 (경로·입력 스키마·응답 코드)
routes/<기능>.ts            HTTP 흐름 — 권한 확인 → 아래 호출 → 상태 코드 선택
lib/*.ts                    여러 표를 함께 바꾸거나 규칙을 판정하는 작업
db/schema.ts                D1 테이블 정의
middleware/*.ts             인증·온보딩·rate limit·접속 기록·최소 버전
```

명세와 구현을 나눈 이유는 길이가 아니다. 한 파일에 두면 어느 쪽을 읽든 다른 쪽을 계속 건너뛰게 되고,
"이 API가 무엇을 약속하는가"(문서와 클라이언트 타입의 출처)를 한눈에 확인할 수 없다.

`lib/`에 올리는 기준은 다음 중 하나에 해당할 때다. 한 줄짜리 조회는 라우트에 그냥 둔다.

- 여러 표를 순서대로 바꾼다 (`delete-account.ts`, `unit-membership.ts`, `leave-merge.ts`)
- 순서나 동시성에 뜻이 있어 설명이 필요하다 (초대코드 소진·충돌 재생성, 관리자 이관)
- 여러 라우트가 같은 판정을 쓴다 (`unit-access.ts`, `leave-balances.ts`)

**오류 처리**: 사용자가 입력을 고쳐 해결할 수 있는 것만 `LeaveRuleError`(`lib/errors.ts`)로 던지고
라우트가 400으로 바꾼다. 그 밖의 오류는 그대로 올려 보내 `index.ts`의 `onError`가 500으로 처리한다.
인프라 장애 메시지가 클라이언트로 새지 않게 하는 경계다.

**캐시**: 응답 캐시는 두지 않는다. KV(`CACHE`)는 이제 관리자 워커의 로그인 시도 제한에만
쓴다 — 사용자 API의 rate limit 카운터는 D1(`rate_limit_counters`)로 옮겼다. KV에는 원자적
증가가 없어 "읽고 더해 쓰기"가 동시 요청에서 겹쳤고, 같이 도착한 요청들이 모두 같은 값을
읽고 써서 **카운터가 한 번만 올라갔다.** 6자 초대코드의 안전이 `3회/15분`에 기대고 있어
그 자리에서는 정밀도 문제가 아니라 실제 구멍이었다. D1의
`INSERT ... ON CONFLICT DO UPDATE SET count = count + 1 RETURNING`은 한 문장이라 원자적이고,
돌려받은 값이 곧 그 요청의 순번이다.
한때 부대 달력을 KV에 캐싱하려던 코드가 있었지만 **읽는 쪽이 끝내 붙지 않았고**,
남은 것은 변경 경로마다 도는 KV 쓰기뿐이어서 걷어냈다. 달력 조회는 지금 D1 왕복 4회다.
다시 캐싱한다면 반드시 캐시 키에 **조회자 id와 차단 목록의 버전**을 넣어야 한다 —
이 응답은 조회자마다 다르고(내 일정 상세, 내가 차단한 사람 제외), 부대 단위로만 캐싱하면
남의 일정이 그대로 새어 나간다. 부대 버전만 올리는 방식으로는 "차단했는데 TTL 동안 계속
보이는" 구멍을 막지 못한다.

**보관 기간**: 접속 기록·푸시 로그는 `LOG_RETENTION_DAYS`(기본 90일)이 지나면 지운다.
만료된 세션도 함께 정리한다. 매일 도는 cron이 `src/index.ts`의 `scheduled` 핸들러를
부르고, 실제 삭제 규칙은 `lib/retention.ts`에 있다. 요청당 한 행이 쌓이는 표라 지우는
곳이 없으면 저장 비용과 관리자 화면 조회가 함께 나빠지고, 무엇보다 "필요한 기간만
보관한다"는 약속을 코드가 지키지 못한다. 한 번에 다 지우지 않고 끊어서 지운다 —
못 지운 몫은 다음 실행이 이어서 한다.

### D1 사용 규칙

**한 문장의 바인드 파라미터는 100개까지다.** 이 상한을 넘기면 `SQLITE_ERROR`로 요청 전체가
죽는다 — 느려지는 것이 아니라 500이 된다. id 목록을 모아 `inArray(...)`에 넣는 조회는
목록이 자라는 순간 이 벽에 부딪히므로, **부대·사용자로 좁히는 조인**으로 쓴다.
`lib/leave-balances.ts`의 `segmentsOfUser`·`segmentsOfUnitDuring`이 그 형태다.
목록으로 조회할 수밖에 없는 자리(`segmentsForLeaves`)는 100개씩 나눠 보낸다.

같은 상한이 **여러 행을 한 번에 넣는 INSERT**에도 걸린다. 이쪽이 훨씬 빨리 부딪힌다 —
행마다 컬럼 수만큼 바인드하기 때문이다. 실제로 났던 것: 휴가 구간 15개(컬럼 7개),
초과 알림 대상 12명(컬럼 9개), 푸시 발송 로그 17건(컬럼 6개). 셋 다 "사람이 늘면
어느 날 갑자기 500"이었다. `lib/d1.ts`의 `insertStatements(db, table, rows)`로 넣으면
표의 컬럼 수에서 청크 크기를 계산해 나눠 준다. **상한은 문장 단위이므로**, 나눈 문장들을
같은 `db.batch()`에 담으면 왕복도 하나로 유지되고 원자성도 그대로다.

**인덱스는 "좁히는 컬럼 + 정렬 컬럼" 순서로 만든다.** 사용자별 목록을 최신순으로 주는
엔드포인트(`/auth/activity`, `/notifications`, `/leaves/mine`)는 정렬 컬럼이 인덱스에 없으면
`USE TEMP B-TREE FOR ORDER BY`가 붙어, LIMIT 50을 돌려주려고 그 사용자의 행을 전부 읽는다.
인덱스를 더하기 전에 `EXPLAIN QUERY PLAN`으로 확인하고, 접두사가 겹치는 인덱스는 만들지 않는다
(`(user_id)`는 `(user_id, created_at)`의 접두사라 중복이다).

**여러 조회를 한 왕복으로 묶을 때는 `db.batch()`를 쓴다.** `Promise.all`은 D1 왕복을
그대로 여러 번 낸다. 서로의 결과에 기대지 않는 조회만 묶는다 — 순서에 뜻이 있는 쓰기를
묶으면 그 뜻이 사라진다.

친구 달력은 선택자를 10명으로 제한해 조회자까지 최대 11개 사용자 id와 네 개 상태만 바인딩한다.
여러 달은 최대 9개월 범위를 한 번 조회한 뒤 월별 응답으로 나누므로 친구별·월별 N+1 요청을 만들지 않는다.

**바인딩**: `wrangler.jsonc`가 실제로 주는 바인딩과 코드가 믿는 `AppBindings`가 어긋나면
`bindings-drift.ts`에서 타입 검사가 깨진다. 생성물은 `pnpm --filter @leave/api types`로 갱신한다.

## 웹 앱의 렌더링 구조

`apps/web`은 한 덩어리가 아니라 두 층이다.

```
공개 페이지 (/, /guide)   빌드 시 HTML로 구워져 정적 자산으로 나간다
법적 고지 (/privacy 등)   손으로 쓴 단독 HTML
그 밖의 모든 주소         worker/index.ts 가 표를 보고 셸(200) 또는 404를 낸다
```

정적 자산과 일치하는 요청은 **워커를 거치지 않는다**(Cloudflare의 기본 동작).
그래서 공개 페이지의 응답 경로에는 워커가 없고, 워커는 SPA 경로와 없는 주소에만
관여한다. 색인 정책·메타데이터·robots.txt·sitemap.xml의 출처는
`src/seo/routes.ts` 한 표다. 이유와 대안 비교는 [seo.md](seo.md).

라우트를 추가하면 그 표에도 넣어야 한다 — 빠뜨리면 그 주소는 404가 되고,
`apps/web/test/seo-routes.test.ts`가 그것을 빌드에서 잡는다.

## 관리자 워커 구조

```
worker/index.ts        보안 헤더 → CSRF → 인증 → 비밀번호 변경 강제 → 라우트
worker/auth.ts         쿠키 세션, 로그인 시도 제한, 권한 미들웨어
worker/audit.ts        감사 로그 (민감 키는 저장 전에 가린다)
worker/routes/*.ts     리소스 하나에 파일 하나
```

접근 단계가 세 겹인 것과 데이터를 바꾸는 모든 라우트가 `writeAudit`을 부르는 것이 이 워커의 핵심이다.
라우트를 추가할 때 두 가지를 지킨다.

1. `operations`에 마운트한다(그래야 세 겹을 모두 통과한다).
2. 변경 라우트라면 변경 전/후 스냅샷과 함께 감사 로그를 남긴다.

리소스마다 파일을 나눈 이유는, 이름만 보고 찾을 수 있게 하기 위해서다.
"공통 CRUD 프레임워크"를 만들지 않는다 — 권한 판정이 눈에 보이는 편이 낫다.

## 관리자 화면 구조

```
src/pages/entity-configs.tsx   리소스별 표시 설정(제목·열·생성 가능 여부)
src/pages/EntityPage.tsx       목록·검색·상세 서랍·삭제 확인 — 리소스와 무관한 흐름
src/components/RecordForm.tsx  어떤 폼을 그릴지 고르는 분기
src/components/record-form/    리소스별 입력과 서버로 보낼 본문
```

새 리소스를 붙이려면 `EntityResource`에 이름을 넣고 `entityConfigs`에 항목을 더한다.
편집까지 필요하면 `EditableResource`에 넣고 `record-form/`에 입력 컴포넌트와 payload 함수를 만든다.
분기를 표로 감추지 않고 `switch`로 두는 이유는, 빠뜨린 것이 컴파일 오류로 드러나게 하려는 것이다.
