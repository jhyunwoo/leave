# Antislop audit 001

Date: 2026-10-05. Repository: `leave`, baseline commit `30be202`.
Mode: **after**, selected by the user for this session.

Follow-up: the user approved all 19 findings for repair. Outcomes and verification are recorded in [audit 002](audit-002-2026-10-05.md). The findings below describe the original baseline.

**Result: the codebase does not fully comply.** This report records 19 findings: 15 HIGH, 2 MEDIUM, and 2 LOW. Finding 14 is conditional on authorship; its character matches alone do not establish a violation.

Priority follows the skill's tiers, rather than security severity: HIGH means Hard Gate, MEDIUM means Purpose-Gate, and LOW means Quality Locks or companion comment hygiene. No application code was changed. Fixes require the user to select finding numbers.

## Scope and method

Reviewed the inventory of all 918 tracked files and searched readable text across web, admin, API, native, shared/client packages, native Kotlin modules, Swift watch/widget targets, scripts, design documents, store metadata, and legal pages. The scan read 808 UTF-8 text files after excluding declaration files, common dependency lockfiles, and binary content. Candidate matches were followed by targeted source inspection. This was not a manual reading of every line.

Applied antislop plugin version 3.2.20, including its code, copywriting, human, UI, and mobile companions. The supplied `DESIGN.md`, `design/brand/README.md`, and project specifications provide real direction. Their green palette, typography, radius choices, Wise inspiration, and requested native glass effects were not treated as violations merely because they resemble common AI defaults.

Built web and admin. Used the project agent-browser workflow for selected Chromium checks on local web/admin pages. Tested public layouts at 320, 390, 768, 1024, and 1440 pixels, selected authenticated states using synthetic local fixtures, and admin dialogs without submitting a destructive action. Fixtures never contacted production.

Native color findings use actual theme/component values and the skill's contrast checker. Native, Android, watch, and widget interfaces were not run on devices or simulators. This audit cannot certify every control, breakpoint, theme, or historical asset approval.

## Numbered findings

### 1. HIGH: Admin system health is asserted without health checks

**Rules: R-36, R-38, C-5.** The dashboard presents unmeasured service health as current fact.

`apps/admin/worker/routes/overview-logs.ts:89` returns literal `"ok"` values for API Worker, D1, R2, KV, and push, with `checkedAt: nowIso()`. The handler reads D1 summary data but does not probe the other services. `apps/admin/src/pages/OverviewPage.tsx:223` renders these values as system status and a last-check time. A successful summary query does not establish the health of all listed services.

Suggested fix: report only measured results, with per-service evidence and check times. Show unknown or unconfigured when no check exists. Remove obsolete service rows if they are not part of the deployed product.

### 2. HIGH: Native muted text fails contrast in both themes

**Rules: R-25, R-34.** Small hints and placeholders use colors below the required 4.5:1 ratio.

`apps/native/src/theme.ts:97` defines light `mute` as `#868685`; its contrast is **3.64:1 on white** and **3.29:1 on `#f2f4f0`**. Dark `mute`, `#8e918c` at line 130, is **4.37:1 on `#2c2c2e`**. `components/field.tsx:50,90` applies these colors to placeholders and 12px hints; `components/next-leave-card.tsx:119` uses muted 12px text on the light canvas. These are normal-sized text, requiring at least **4.5:1**.

Suggested fix: adjust the muted text tokens against each actual surface, then check both themes and component states. These are source-based calculations, not a native runtime certification.

### 3. HIGH: Web input placeholders fail contrast

**Rule: R-25.** Placeholder text is too pale on white inputs.

`apps/web/src/styles/global.css:59,671` sets `--muted-soft: #9a9c99` and applies it to `.input::placeholder`. Its contrast on white is **2.77:1**, below both the normal-text 4.5:1 and large-text 3:1 thresholds. The login/signup input styles were confirmed in the browser.

Suggested fix: use a darker placeholder token. Keep labels and field instructions independently readable.

### 4. HIGH: Failed requests are presented as empty data

**Rule: R-27.** Error responses produce messages that falsely imply a successful, empty result.

`apps/web/src/pages/LeavesPage.tsx:193,203` branches from pending directly to missing/empty data. `NotificationsPage.tsx:222,232` similarly renders no notifications when the request fails. The native counterparts have the same pattern in `screens/leaves.tsx:268,272` and `screens/notifications.tsx:253,287`.

Browser checks with synthetic **403** responses confirmed empty leave and notification messages. Suggested fix: handle `isError` before the empty branch, provide retry feedback, and distinguish unavailable data from a successfully fetched empty list.

### 5. HIGH: Failed requests leave several screens spinning

**Rule: R-27.** Missing data is treated as loading even after an error has settled.

`apps/web/src/pages/LeaveGrantsPage.tsx:33`, native `screens/leave-grants.tsx:68`, and native `screens/profile-edit.tsx:84` return a loading view whenever the query is pending **or has no data**. Failed initial requests have no data indefinitely. A browser check with a synthetic **403** confirmed that web grants stayed on its spinner without an error or retry action.

Suggested fix: separate pending, error, empty, and success branches. Preserve previous data deliberately when a background refresh fails.

### 6. HIGH: Admin modal focus and Escape behavior are broken

**Rules: R-32, R-26.** Keyboard focus escapes modal content, and Escape leaves a confirmation open.

`apps/admin/src/components/ui.tsx:288` implements Drawer without focus entry, containment, background inertness, or restoration. `ConfirmDialogBody` at line 389 has no Escape handler or focus containment. After waiting for drawer animations to finish, browser checks confirmed: opening a drawer left focus on the background row; Tab from its last button reached the document body; Shift+Tab escaped the confirmation; and Escape closed the underlying drawer while leaving the confirmation open.

Suggested fix: implement shared modal focus behavior and ensure only the topmost dialog handles Escape. Restore focus to the invoking control. The destructive confirmation was cancelled; no delete request was submitted.

### 7. HIGH: Admin table rows lack a clearly visible focus indicator

**Rule: R-32.** Keyboard-operable rows suppress their outline and replace it with an almost invisible fill.

`apps/admin/src/styles/global.css:775` gives focused rows `outline: 0` and background `#f7faf5`. That background differs from white by only **1.05:1**. Browser inspection confirmed the focused row had no outline or box shadow.

Suggested fix: add a distinct `:focus-visible` ring or similarly clear indicator, preserving the row's existing Enter behavior.

### 8. HIGH: The guide's overflowing table is inaccessible by keyboard

**Rule: R-32.** On narrow screens, users cannot focus the table's horizontal scroll region.

`apps/web/src/pages/GuidePage.tsx:145` renders `.guide-table-wrap` without keyboard focus or focusable descendants. `pages/guide.css:156,165` enables horizontal scrolling around a table with a **520px** minimum width. At a **320px** viewport, axe 4.12.1 reported `scrollable-region-focusable` on this wrapper. The document itself did not overflow; the defect is access to the internal scroll area.

Suggested fix: provide a named, keyboard-focusable scroll region with visible focus, or reflow the table so horizontal scrolling is unnecessary.

### 9. HIGH: Several mobile targets are smaller than 44px

**Rule: R-03.** Common controls fall below the skill's **44 by 44px** touch target requirement.

At 390px, browser measurements found a **40px-high** landing navigation CTA, **32px-high** footer links, **34px-high** app navigation tabs, and a **36 by 36px** profile link. Relevant styles are `pages/landing.css:66,635` and `styles/global.css:966`. `components/Modal.tsx:180` constrains its close button to 36px wide. Native `components/time-picker.native.tsx:219,239` uses 36px preset/clear targets without additional `hitSlop` on those Pressables.

Suggested fix: expand effective hit areas to at least 44px in both dimensions while keeping spacing comfortable. Do not count visual dimensions alone where an existing `hitSlop` already supplies a sufficient target.

### 10. HIGH: Published privacy descriptions contradict sharing behavior

**Rule: R-38, C-5.** Different public surfaces describe different visibility rules for private schedule details.

English store metadata says schedule titles and notes can be visible to group members: `store/metadata/appstore.en.md:41,75` and `googleplay.en.md:33,51`. `apps/web/public/terms.html:6` and its store mirror similarly describe titles, reasons, and notes as potentially group-visible. Korean store copy says titles, reasons, and drafts are private. `apps/api/src/lib/calendar.ts:235` filters detailed calendar leaves to `userId === viewerId`; the shared attendee projection omits those private fields.

Suggested fix: reconcile public descriptions with the verified sharing contract across API routes. Update both legal mirrors and all store languages together. Do not change sharing permissions simply to match stale copy.

### 11. HIGH: Signup and public eligibility copy disagree on minimum age

**Rule: R-38.** The product presents **14** and **18** as different minimum ages.

Web `pages/SignupPage.tsx:48,176` and native `screens/signup.tsx:48,152` require confirmation of age 14 or older. `pages/LandingPage.tsx:214` and `public/terms.html:4`, mirrored in store legal content, describe the service as for age 18 or older.

Suggested fix: have the owner choose the actual eligibility policy, then align consent text, enforcement, terms, FAQ, and store audience settings. This finding identifies a product contradiction; it does not determine the legally correct age.

### 12. HIGH: The 60-second signup promise has no supplied evidence

**Rules: R-17, R-36.** A precise performance promise appears without a supporting measurement.

Web `pages/SignupPage.tsx:98` and native `screens/signup.tsx:98` say users can start within **60 seconds**. The flow includes email verification and onboarding. No timing study or source for that promise was found in the repository. This establishes an evidence gap, not proof that every signup exceeds 60 seconds.

Suggested fix: use an untimed description or provide measured evidence defining the start/end points and relevant conditions.

### 13. HIGH: Landing examples misrepresent the capacity calculation

**Rule: R-38.** The mockup teaches behavior that contradicts the real calculation.

`pages/LandingPage.tsx:47` says the daily maximum is **4**, while sample cells at lines 32-36 use denominators of **3**. Lines 89 and 485 call **3/3** an exceeded limit. `packages/shared/src/availability.ts:43` marks a day exceeded only when `count > allowed`; equality is within the limit, as the guide also explains.

Suggested fix: make the illustration's limit, counts, status colors, and notification text use the same real rule. CSS/SVG mockups are already authorized by the design specification; the issue is their incorrect content.

### 14. HIGH, CONDITIONAL: Em dashes remain throughout product copy

**Rule: R-02.** The skill bans em dashes in agent-authored text, with explicit exceptions for rule documentation and owner direction.

Examples occur in `pages/LandingPage.tsx:222`, `pages/GuidePage.tsx:58,90,390`, `apps/admin/src/components/record-form/LeaveFields.tsx:85`, and `store/metadata/appstore.en.md:20`. The text scan found **1,841 matches across 459 files**, excluding `DESIGN.md` and agent instruction directories. This is a candidate count, not 1,841 established violations: authorship and owner-approved voice overrides were not verified.

Suggested fix: identify agent-authored copy and any recorded owner exceptions before changing punctuation. Preserve supplied design prose and rule documentation. Do not bulk-rewrite every character match.

### 15. MEDIUM: Selected admin visual techniques lack written purpose

**Rules: R-01, R-04.** Purpose is plausible, but the skill requires it to be written down.

`apps/admin/src/styles/global.css:190` uses a gradient for active navigation. `pages/OverviewPage.tsx:238` uses the generic lightning `Zap` icon for KV cache. No specific written explanation for these choices was found in the design material. Gradients and icon libraries are allowed; their mere presence is not a violation.

Suggested fix: record the actual hierarchy/content reason for these choices, or use a simpler treatment if no useful reason exists. This is a documentation gap, not a demonstrated usability failure.

### 16. MEDIUM: Required design dials are not declared

**Rule: R-19 and core Part 3.** The mandated ENERGY, RHYTHM, and MOTION declarations are absent.

No explicit dial declarations were found in tracked text, and no documented Design Read was located. Direction itself exists, so this is not an R-37 missing-direction finding. Reduced-motion handling is present in web and native code, but consistency with a declared MOTION dial cannot be checked.

Suggested fix: record a Design Read and explicit dials grounded in the existing owner direction. Then assess animation purpose and section rhythm against them; do not invent a new visual direction.

### 17. LOW: Comments violate the companion's concise-note rules

**Rule: R-31 as referenced by antislop-code's Decorative Separators; companion mandatory comment rules.** Long explanatory headers and decorative banners add avoidable reading load.

Examples include the long headers in `apps/web/src/App.tsx:1`, `components/Modal.tsx:1`, `apps/native/src/theme.ts:1`, and `packages/client/src/query-policy.ts:1`. `packages/client/src/hooks/leaves.ts:56` uses three-line decorative section separators. Several comments contain useful implementation constraints, so removing them wholesale would lose information.

Suggested fix: retain the platform, security, protocol, and business-rule facts in one line, or two when the second adds a fact. Remove ornamental separators and redundant narration. Keep executable code untouched during comment cleanup.

### 18. LOW: Signup CTAs use generic action copy

**Rule: R-15.** Repeated “start for free” wording does not name the destination action.

`pages/LandingPage.tsx:368,391,584` uses `무료로 시작하기` for signup links. `pages/GuidePage.tsx:324,377` repeats it. The links work; the finding concerns specificity, not navigation.

Suggested fix: use an action such as `계정 만들기` where the destination is account creation, checking the actual flow before choosing wording.

### 19. HIGH: The admin period selector cannot change anything

**Rule: R-26.** A displayed filter is a nonfunctional control.

`apps/admin/src/pages/OverviewPage.tsx:159` renders a period select with only the “today” option and no change handler. It cannot select a different period or affect the displayed logs. There is no visible unfinished-feature label.

Suggested fix: display the current period as text, or implement supported period choices that actually update the data.

## Verification record

### Build and analysis

- **PASS:** `pnpm --filter @leave/web --filter @leave/admin build` completed successfully, including web type checking, Vite/SSR/SEO output, and admin client/worker builds.
- **PASS:** `NODE_OPTIONS=--max-old-space-size=4096 pnpm --filter @leave/native check-types` completed with exit 0. An earlier attempt was interrupted, and the default-heap retry exited 134 with a Node heap exhaustion error. The successful retry produced no type diagnostics. Native compilation is not a substitute for device accessibility testing.
- **PASS:** the skill's `contrast-check.py` reproduced the native and web contrast ratios in findings 2 and 3.
- **PASS, scoped:** sampled landing/guide layouts had document scroll width equal to viewport width at 320, 390, 768, 1024, and 1440px. The guide contains a separate overflowing table region.

### Recorded browser actions and states

- Landing signup navigation reached `/signup`; guide navigation reached `/guide`.
- Login submission showed a visible fetch error when the local fixture could not complete it. This was not a successful real login test.
- Settled signup at 390px had **zero axe violations**. An earlier contrast warning during its entrance animation disappeared after the animation settled and is excluded from the findings.
- Landing at 390px had zero axe violations and one incomplete contrast check. Zero automated violations is not proof of full compliance.
- Guide at 320px produced the keyboard scroll-region violation in finding 8 and incomplete table contrast checks.
- With denied data requests, web leaves and notifications rendered empty messages; grants remained on a spinner.
- The web modal checked entered focus, made the app root inert, and closed with Escape.
- An admin user row opened its drawer. Keyboard checks exposed escaped focus and the nested Escape failure described in finding 6. Cancel closed the confirmation. No destructive submission was performed.
- Settled admin users at 390px fit the viewport. An automated table-header warning was not promoted to a finding because accessible naming needed further validation.

The full browser/E2E suites were not run. Real login, email delivery, push, every authenticated route, every admin mutation, all native controls, and both native themes at runtime remain outside the verified coverage. Local fixture failures were intentional and are not evidence of a production outage.
